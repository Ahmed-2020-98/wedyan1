# المسارات

## مسار الشراء — لوحة جاهزة

```
تسجيل → دخول → تصفّح المعرض → صفحة اللوحة → السلة → إتمام الطلب
      → بوابة الدفع → خطّاف موثَّق → الطلب مدفوع → تجهيز → شحن → تسليم
```

### الحالات

`pending` · `payment_pending` · `paid` · `processing` · `preparing` ·
`shipped` · `delivered` · `cancelled` · `refunded`

الانتقالات المسموحة معرّفة في `App\Enums\OrderStatus::allowedTransitions()`
ويُتحقق منها في الخادم — لوحة التحكم تستطيع إرسال أي قيمة، وطلب ينتقل من
«ملغى» إلى «تم الشحن» يجب أن يُرفض.

### المخزون

اللوحة الجاهزة قطعة واحدة. عند إتمام الطلب:

1. تُقفل صفوف اللوحات (`lockForUpdate`) داخل معاملة واحدة.
2. يُخصم المخزون وتصبح الحالة **`reserved`** لا `sold` — البيع لم يكتمل بعد.
3. عند وصول خطّاف موثَّق بالدفع تصبح **`sold`** ويزيد `sold_count`.
4. عند الإلغاء أو فشل الدفع يعود المخزون وتعود **`available`**.

القفل هو ما يمنع بيع اللوحة مرّتين لو أتمّ زبونان الطلب في اللحظة نفسها؛
الثاني يقرأ المخزون بعد خصمه فيفشل بوضوح بدل أن يُكتشف الأمر عند الشحن.

### الإجماليات

```
الإجمالي الفرعي → − الخصم → + الشحن → + الضريبة على (الفرعي − الخصم + الشحن)
```

الضريبة بعد الخصم لا قبله: حسابها على المبلغ الكامل يحمّل الزبون ضريبة مبلغ
لم يدفعه. والخصم مقيَّد بسقفه وبقيمة الطلب نفسه، فلا يصير الإجمالي سالباً.

## مسار الحجز — لوحة تُرسم خصيصاً

```
طلب حجز → قيد المراجعة → قبول الفنان (يحدّد السعر) → بانتظار العربون
        → دفع العربون → قيد التنفيذ → تحديثات المراحل بالصور
        → اكتملت اللوحة → دفع المتبقّي → جاهزة للتسليم → شحن
```

### الحالات

`pending` · `under_review` · `accepted` · `rejected` · `deposit_pending` ·
`in_production` · `completed` · `ready_for_delivery` · `cancelled`

### ما يميّزه عن الطلب العادي

**لا سعر عند الطلب.** اللوحة المخصّصة تُسعَّر بعد أن يفهم الفنان المطلوب،
لا قبله. ولذلك لا يوجد دفع في خطوة الطلب إطلاقاً، ولا حقل سعر في نموذجها.

**دفعتان لا واحدة.** العربون يبدأ الإنتاج، والمتبقّي يُجهّز اللوحة للتسليم.
كلتاهما صفّان في `payments` تخصّان الحجز نفسه.

**المبلغ يُحسب في الخادم.** `Reservation::amountDueNow()` تقرّر: قبل أي دفع
المستحقّ هو العربون، وبعده المتبقّي. لا يُقرأ أي مبلغ من الطلب — وإلّا لأمكن
للزبون إرسال ريال واحد واعتبار لوحته مدفوعة.

**سجلّ المراحل هو المنتج.** انتظار خمسة أسابيع يحتمله الزبون لأنه يرى تقدّم
عمله. لذلك `reservation_updates` تحمل صورة ونسبة إنجاز، ولها راية
`is_visible_to_customer` تفصل ملاحظات الفنان لنفسه عمّا يُعرض.

### الانتقالات التلقائية

| الحدث | الأثر |
|-------|-------|
| بدء الدفع من الزبون | `accepted` → `deposit_pending` |
| خطّاف دفعة أولى موثَّق | `accepted`/`deposit_pending` → `in_production` |
| الفنان يُعلن الاكتمال | `in_production` → `completed` (الإنجاز ١٠٠٪) |
| خطّاف الدفعة الأخيرة | `completed` + مسدَّد بالكامل → `ready_for_delivery` |

دفعة تصل في منتصف الإنتاج تُسجَّل ولا تُحرّك الحالة.

## مسار الدفع

```
إنشاء الطلب/الحجز → payments (pending)
   → المزوّد ينشئ العملية → processing → إعادة توجيه الزبون
   → [ الزبون يدفع على نطاق المزوّد ]
   → خطّاف إلى /payments/webhook/{gateway}
   → التحقق من التوقيع → تسجيل الحدث → تطبيق النتيجة
```

**حالة الطلب لا تتقدّم إلا من خطّاف موثَّق.** إعادة التوجيه في المتصفح لا
تُغيّر شيئاً — من يعود منه يستطيع تحرير العنوان. صفحة النتيجة تسأل خادمنا،
وهو يستجوب المزوّد إن لم يكن الخطّاف قد وصل بعد (`PaymentService::synchronise`).

**جالب للثبات.** المزوّدون يعيدون إرسال الخطّاف عند أي شكّ في التسليم.
`applyResult` يقفل صف الدفعة ويخرج فوراً إن كانت مدفوعة أصلاً، فلا يتضاعف
المخزون ولا المبيعات. وكل محاولة تُسجَّل في `payment_transactions` ولو لم
تُغيّر شيئاً — هذا هو سجلّ التدقيق.

### حالات الدفع

`pending` · `processing` · `paid` · `failed` · `cancelled` ·
`refunded` · `partially_refunded`

---

## المراجعات

لا مراجعة بلا شراء موثَّق (إعداد `reviews.require_purchase`). كل مراجعة تبدأ
`pending` وتُنشر بعد الاعتماد، وتعديلها يُعيدها إلى الانتظار — نصّ اعتُمد ثم
تغيّر يجب أن يُراجَع ثانيةً. متوسط التقييم يُعاد حسابه من المعتمدة وحدها.
